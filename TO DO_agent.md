## How this file works
- Each `##` heading in the Features part matches a feature line in `TO DO.md` exactly (without the status text after " — ").
- Under a heading: ordered `- [ ]` / `- [x]` / `- [-]` tasks, nested as deep as needed, plus free-form `Notes:` bullets (context, file paths, gotchas).
- A task that can't start until a human task is done says so inline: `(needs 👤: <exact human task text>)`.
- A feature heading with only `Notes:` and no checkboxes hasn't been started. The agent that starts it writes the tasks.
- Everything under `# Reference` at the bottom is context only. Nothing there counts as a task.

## GameSceneInteractionTests.testTappingFarOutsideTheBoardDeselectsWithoutMoving fails
- [x] Fixed — and it turned out to be a real product bug, not only test flakiness
Notes:
- **Root cause was a genuine save/delete race in production.** `saveGameStateToFile` wrote via a fire-and-forget `Task.detached` while `deleteGameFile` removed the file synchronously, and nothing ordered the two. `finalizeMove` does both in one pass — every move saves, and the game-over branch then deletes — so an in-flight save could land *after* the delete and leave a finished game on disk, to be offered as a resumable game on the next launch. The failing test was that race showing up somewhere it could be observed.
- Diagnosis: the test failed with `selectedPiece` nil *and* `currentPlayer` already "black" on what should be a fresh board — i.e. the scene had loaded the previous test's half-played save, where f5's pawn had already moved to f6. Tests run alphabetically, so `testSelectingAndMoving…` always precedes it.

Same explicit-chaining reason as `GameScene`'s `CPUSearchExecutor`: Swift guarantees no FIFO order for suspended actor callers, so a bare actor would not have fixed this. The lock guards only the tail pointer, so enqueue order follows call order from any thread while the I/O stays off the main thread.

- `GameFileStore.flush()` drains the queue; the test's `setUp`/`tearDown` are now `async` and await it before deleting.
- Gotcha worth remembering: taking an `NSLock` directly inside an `async` function warns "unavailable from asynchronous contexts" and is an **error under the Swift 6 language mode**. The locked read lives in a separate non-async `currentTail()` for that reason.

GameState is a plain value type, so splitting root moves across threads — each on its own board copy with its own worker GameCPU/transposition table, sidestepping the need to make transpositionTable thread-safe — is mechanically straightforward in Swift. (2) The standard fix (Young Brothers Wait Concept: search the best-ordered move first and alone to establish a real bound, then test the rest in parallel with a cheap null window, re-searching only the rare fail-highs) was implemented and is correct — it matched the sequential search's evaluation exactly in testing — but was still 2.17x SLOWER in wall-clock time at depth 5 (22.8s vs 10.5s), because this engine's move-ordering heuristic (capture-value difference only, no killer-move/history heuristics) isn't strong enough to keep the "first move is (near) best" assumption reliable, so too many of the "remaining" moves fail high and need an expensive sequential re-search, and even the ones that don't still cost more than a cheap rejection should. Conclusion: parallel root search isn't worth adopting until move ordering is meaningfully stronger — worth revisiting after killer-move/history-heuristic ordering is added, but not before.)

Left as a documented, not-fixed-here gap: `eloScore` is still fully client-computed and self-written (`MultiplayerManager.updateElo`) — the new rules restrict which fields a client may touch but can't validate the new Elo value itself, so a modified client could still self-report an inflated Elo; actually closing that would require moving Elo adjustment into a Cloud Function, a separate, larger change. ##### Bugs
- (done) GameCPU can wrongly conclude it has no legal moves mid-game, well before an actual checkmate/stalemate: in a self-play smoke test (30 games, `.hard` difficulty, see the self-play dataset item in Update 1.6 above), `GameCPU.findMove` returned nil at ply 64 of one game while `GameState.hasLegalMovesForCurrentPlayer()` (the slower make/unmake ground-truth check) confirmed White genuinely had legal moves. The `isPinned`/`filterMovesThatExposeKing` fast path (originally suspected) turned out to be correct — the real cause was in `minimax`'s transposition-table lookup (GameCPU.swift): a cached entry with `depth >= depth` and an `.exact`/cutoff-triggering flag returned early with `(entry.value, nil)` even at the search root, and `minimaxMove`'s iterative-deepening loop only updates `bestMove` when a non-nil move comes back — so once pondering (see the "Do CPU calculations in the background" item above) had already populated an exact/cutoff TT entry for the current root position, every iterative-deepening depth for the real move search could hit that same shortcut and hand back a nil move, leaving `findMove` with nothing to return despite legal moves existing.
