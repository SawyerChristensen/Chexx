## How this file works
- Each `##` heading in the Features part matches a feature line in `TO DO.md` exactly (without the status text after " — ").
- Under a heading: ordered `- [ ]` / `- [x]` / `- [-]` tasks, nested as deep as needed, plus free-form `Notes:` bullets (context, file paths, gotchas).
- A task that can't start until a human task is done says so inline: `(needs 👤: <exact human task text>)`.
- A feature heading with only `Notes:` and no checkboxes hasn't been started. The agent that starts it writes the tasks.
- Everything under `# Reference` at the bottom is context only. Nothing there counts as a task.

- (done) GameCPU can wrongly conclude it has no legal moves mid-game, well before an actual checkmate/stalemate: in a self-play smoke test (30 games, `.hard` difficulty, see the self-play dataset item in Update 1.6 above), `GameCPU.findMove` returned nil at ply 64 of one game while `GameState.hasLegalMovesForCurrentPlayer()` (the slower make/unmake ground-truth check) confirmed White genuinely had legal moves. The `isPinned`/`filterMovesThatExposeKing` fast path (originally suspected) turned out to be correct — the real cause was in `minimax`'s transposition-table lookup (GameCPU.swift): a cached entry with `depth >= depth` and an `.exact`/cutoff-triggering flag returned early with `(entry.value, nil)` even at the search root, and `minimaxMove`'s iterative-deepening loop only updates `bestMove` when a non-nil move comes back — so once pondering (see the "Do CPU calculations in the background" item above) had already populated an exact/cutoff TT entry for the current root position, every iterative-deepening depth for the real move search could hit that same shortcut and hand back a nil move, leaving `findMove` with nothing to return despite legal moves existing.
