(Added an optional `priorityFromSquare` to `GameCPU.ponder`/`minimax`: when set, root move ordering puts moves starting from that square first (via a new `prioritizeMoves` helper), so those branches get searched/deepened/cached before other root moves within each ponder time slice. Wired into GameScene's `selectNewPiece` — every time the human taps one of their own pieces, `restartPonderingPrioritizing(col:row:)` restarts the background ponder pass biased toward that piece's square, since it's the piece they're most likely about to move. ## ⚙️ Other Changes

### Bugs
- [x] GameCPU can wrongly conclude it has no legal moves mid-game, well before an actual checkmate/stalemate: in a self-play smoke test (30 games, `.hard` difficulty, see the self-play dataset item in Update 1.6 above), `GameCPU.findMove` returned nil at ply 64 of one game while `GameState.hasLegalMovesForCurrentPlayer()` (the slower make/unmake ground-truth check) confirmed White genuinely had legal moves. The `isPinned`/`filterMovesThatExposeKing` fast path (originally suspected) turned out to be correct — the real cause was in `minimax`'s transposition-table lookup (GameCPU.swift): a cached entry with `depth >= depth` and an `.exact`/cutoff-triggering flag returned early with `(entry.value, nil)` even at the search root, and `minimaxMove`'s iterative-deepening loop only updates `bestMove` when a non-nil move comes back — so once pondering (see the "Do CPU calculations in the background" item above) had already populated an exact/cutoff TT entry for the current root position, every iterative-deepening depth for the real move search could hit that same shortcut and hand back a nil move, leaving `findMove` with nothing to return despite legal moves existing. Fixed by gating the TT early-return on `!isRoot`, so the root always finishes generating and searching real moves regardless of what's cached; non-root nodes (which only need to bubble a value up, not a move) are unaffected and still benefit from the cutoff. Verified with a standalone `swiftc -O` driver (mirroring the CPU benchmark/self-play harness methodology used elsewhere in this doc): replaying the exact reproduction position from `~/DeckedOutCollection/ChexxSelfPlayDataset.md` now returns a real move instead of nil, and a full from-scratch self-play game that reliably hit the bug by ply ~66 against the old (HEAD) GameCPU.swift no longer does against the fixed version. Also covered by the full `ChexxTests` suite (19 tests, 0 failures) and a clean, warning-free Debug build.
